# 切りのいいところで `/clear` を促す

コンテキストを小さく保つため、切りのいいところで、残りの作業がすべて beads にあり、git に未コミットのものがないことを確かめてから、ユーザーに `/clear` を促す。会話が長くなると、1 ターンが遅く高くなり、古い経緯に引きずられた判断もしやすくなる。状況は beads と git に残るので、会話を消しても続きから再開できる（再開の手順は handoff.md）。

## 切りのいいところ

次のいずれかに当たるとき。

- ひとまとまりの作業（1 つの Issue、1 本の PR、依頼された一連の課題）が終わった。
- ユーザーの判断や作業を待つ状態になり、自分だけで進められることが残っていない。
- 会話が長くなった（多くの Issue をまたいだ、要約が入った、長いログや大きなファイルを何度も読んだ）。作業の途中でも、次の区切りまで進めたら促す。

作業の途中（テストが落ちている、変更を半分だけ入れた、PR の CI を待っていて結果で次の手が変わる）では促さない。区切りまで進めてからにする。

## 促す前に確かめること

handoff.md の「停止前にすること」を済ませたうえで、次を上から順に確かめる。1 つでも満たせなければ、満たしてから促す。満たせない理由があるときは `/clear` を促さず、何が残っているかを伝える。

1. **残りの作業がすべて beads にある**
   - `bd list --status=in_progress` と `bd ready` を見て、この会話で分かった残りの作業（やり残し、後回しにしたこと、見つけた不具合、確認待ち）が、どれかの Issue になっている。なければ `bd create` で作る。
   - 進行中の Issue の note に、終わったこと、残っていること、次にやること、関係するファイルと PR が書いてある。
   - ユーザーに尋ねていることは、質問と選択肢と自分の推奨を、該当する Issue の note に書いてある。会話にしかない質問を残さない。
   - 次の会話で要る知見（落とし穴、環境の事情）は `bd remember` で残してある。
2. **git に未コミットのものがない**
   - `git status --short` が空である。完了した変更は、git の運用ルールに従ってコミットし、push してある。
   - 未完了で壊れている変更が残るときは、促さない。区切りまで進めてコミットするか、残っている変更と理由をユーザーに伝える。
   - 作業ブランチにいるときは、そのブランチと PR の番号が Issue の note にある。push していないコミットがない（`git status --short --branch` に ahead が出ない）。
3. **動いているものが残っていない**
   - バックグラウンドのコマンドやエージェントが終わっている。結果を待っているものがあれば、受け取って反映してからにする。

## 促し方

最後のメッセージの終わりに、次の 3 つを書く。

- 残りの作業は記録済みで、未コミットの変更がないこと。
- `/clear` を実行してほしいこと（コンテキストを小さく保つため）。
- 再開するときに何と言えばよいか（例: 「続きを進めて」。返事待ちの質問があれば、その答えを添えてもらう）。

例:

```
残りの作業はすべて記録してあり、未コミットの変更はありません。
コンテキストを小さく保つため、ここで `/clear` を実行してください。
再開するときは、上の 1〜3 の返事を添えて「続きを進めて」と伝えてください。
```

- `/clear` は Claude Code からは実行できない。促すだけにする。
- ユーザーへの質問があるときは、質問を先に書き、そのあとに `/clear` を促す。返事は `/clear` のあとでよいと書く。
- 促したあとにユーザーが `/clear` せずに続けたときは、そのまま作業を続ける。次の切りのいいところで、もう一度だけ促す。
- beads の操作（Issue の ID、note、`bd remember`）は、ここでもメッセージに書かない（beads.md）。
