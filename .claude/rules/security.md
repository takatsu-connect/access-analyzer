# セキュリティの規則（設計・構築・運用で常に守る）

この BI はログインなしで誰でも見られ、リポジトリは public である。守る資産は、訪問者のプライバシー、秘密情報（GA4 への認証、Supabase のバッチ用接続文字列、Vercel の環境変数）、BI データの完全性の 3 つ。脅威モデルの全体は .claude/agents/security-auditor.md にある。ここにあるのは、判断せずに守るだけでよい規則。外れる必要があるときは ADR に理由を書き、security-auditor のレビューを受ける。

## 公開するデータ

- 公開するのは集計値だけ。次元は、記事、著者の表示名、カテゴリ、タグ、日付（日・曜日・時間帯）、デバイス種別、流入チャネル、参照元ドメイン、都道府県と市区まで。これ以外の次元を足すときは要件に ID を付けて追加し、security-auditor のレビューを受ける。
- 記事・著者の数字の比較の相手は、前の期間、全体の分布（中央値、四分位の帯）、その著者自身の過去の記事の 3 つだけ。
- 出さないもの: ユーザー ID やクライアント ID、完全な参照 URL、サイト内検索語、フォームの送信内容、IP アドレス、市区より細かい地域、リアルタイムの値。
- 小さな数は格納時に伏せる。しきい値は要件（NFR）で決めた値を使う。読み出し側で丸めて済ませない。
- 非公開、下書き、パスワード付きの記事は取り込まない。WP REST API が公開している範囲が BI の範囲。削除や非公開化された記事は、次のバッチで BI からも消す。
- 著者について保存・表示するのは、サイトが公開している表示名と著者ページの URL だけ。メール、ログイン名、WordPress のユーザー ID は保存もしない。
- ライター同士の順位表は出さない。有効化する設定も持たない（公開 BI では「運営が見る」と「全員が見る」が同じになる）。比較は全体の分布（中央値、四分位の帯）と、その著者自身の過去の記事に限る。著者を数値で並べ替えられる表も作らない。
- ライター本人が非表示を申し出たときに除外する著者の一覧は、public リポジトリに置かない。環境変数または Supabase の非公開テーブルに置き、除外されていること自体が画面から分からない形にする。

## 秘密情報

- 鍵、トークン、パスワードはリポジトリに置かない。渡す経路は GitHub Actions の Secrets と Vercel の環境変数だけ。.env.example には項目名だけを書く。
- ローカルの鍵は credentials/ または .env に置く。どちらも .gitignore 済み。別の場所に置かない。
- GA4 の認証は Workload Identity Federation で行う。サービスアカウントの JSON 鍵を作らない。
- Supabase へのアクセスはサーバー側（Actions と Vercel のサーバー）だけ。ブラウザに渡る名前（`NEXT_PUBLIC_` など）に Supabase のキーを入れない。
- データベースへの接続は接続先の証明書を検証する（`sslmode=verify-full`）。下げるときは ADR に理由を書き、security-auditor のレビューを受ける。
- 秘密を含みうる値を、ログ、エラーメッセージ、コミットメッセージ、Issue、文書に書かない。
- 秘密が git 履歴に入ったら、履歴を消すより先に無効化と再発行をする。

## Supabase

- すべての表で RLS を有効にする。anon ロールには、公開用のビューまたは表に対する select 以外の権限を与えない。
- 自動の書き込みは専用ロール `batch_writer` だけが行う。権限とポリシーは表の名前を列挙して与え、`all tables in schema`、`alter default privileges ... to`、`bypassrls` を使わない。除外リストと公開ビューには何も与えない。service role キーは使わず、どこにも置かない。
- 手動の書き込みは、運用手順の固定の SQL で除外リストの行を変える場合に限る。ロールのパスワードは運用手順で設定し、マイグレーションとシードに書かない。この 2 つの操作は、次項の手変更の禁止の例外とする。スキーマと権限の変更はこの例外に含めない。
- スキーマの変更はマイグレーションファイルで行い、リポジトリに入れる。ダッシュボードでの手変更をしない。
- `security definer` の関数やビューは、公開してよい列だけを返すことを確かめてから使う。

## GitHub Actions

- ワークフローの先頭で `permissions:` を宣言し、既定は `contents: read`。`id-token: write` は認証するジョブだけに付ける。
- `pull_request_target` を使わない。fork からの PR で Secrets に触れる経路を作らない。
- サードパーティの Action は commit SHA で固定し、コメントにバージョンを書く。更新は Dependabot で行う。
- ログに出すのは件数、所要時間、エラーの種別まで。API の応答、行データ、トークンを出さない。public リポジトリのログは誰でも読める。
- 定期実行は main ブランチだけで動かす。

## BI アプリ（Vercel）

- 利用者が与えるパラメータ（期間、記事 ID、著者、カテゴリ）は、型と範囲を検証してから使う。問い合わせに文字列として埋め込まない。
- 応答ヘッダを設定する: Content-Security-Policy、X-Content-Type-Options: nosniff、Referrer-Policy、frame-ancestors（または X-Frame-Options）。
- エラー応答に、スタックトレース、内部の URL、SQL を出さない。
- 外部へのリンク先は takatsu-connect.com に固定する。利用者の入力からリンク先を作らない。
- データは日次でしか変わらないので、ページはキャッシュして配信し、リクエストごとに Supabase に問い合わせない。

## 依存

- ロックファイルをコミットする。Dependabot を有効にする。
- 致命的または高の脆弱性が残った状態でデプロイしない。
- 依存を足すときは、必要性と保守の状況を確かめ、コミットメッセージに理由を書く。

## 対象サイトへの配慮

- WP REST API への問い合わせは日次バッチだけ。間隔を空け、必要な記事だけを差分で取る。
- 対象サイトと本番の BI に、スキャンや負荷試験などの能動的な試験をしない。

## 確認の流れ

- 要件と設計の確定前、初回公開前、.github/workflows/ や Supabase の権限や認証に触れる変更のあと、定期点検のときに、security-auditor に監査を依頼する。
- 致命的と高の指摘は Issue にして、修正してから次の工程へ進む。
