## 結論

**設計を進めてよい。** 致命的 0 件、高 0 件、中 4 件、低 7 件。中の 4 件は ADR の確定までに反映するか、受け入れる理由を ADR に書く。

中継が国外からの WordPress への踏み台になる経路は、設計の上では見つからなかった。

- 未認証の相手は WP に届かない。トークンを持つ相手でも、届くのは許可リストの GET だけで、ログイン画面、`wp-admin`、`xmlrpc.php` には届かない。
- 転送先のホストとスキームは定数で、入力から作らない。SSRF の経路はない。
- 残る弱点は、許可リストの「キーの必須」の抜け（M-1）、中継のコードそのものを差し替えられるプレビューの経路（M-2）、トークンの無効化の確実さ（M-3）、漏えい時の上限と検知のなさ（M-4）である。

影響の見積もりの前提として、守る相手は公開済みのデータで、中継が新たに開示する情報はない。また、ADR 0011 の試験が示すとおり国外制限は「日本の IP かどうか」の判定なので、hnd1 の出口を使うことは第三者でも自分の Vercel アカウントで同じようにできると考えられる（Vercel の出口 IP が利用者間で共有かは未確認）。中継の悪用で攻撃者が得るものは小さく、主な損失は対象サイトへの負荷と Vercel の費用である。重要度はこれを踏まえて付けた。

## 指摘

### 致命的

なし。

### 高

なし。

### 中

#### M-1 `_fields` が必須と書かれておらず、省くと全項目が返る

- 対象: ADR 0011 §2（51、55-58、65 行）、§結果（180 行）
- 問題: 許可リストは「これ以外のキーがあれば 400」と「値の完全一致」を定めているが、キーを**省いた**ときの扱いがない。`_fields` を付けない `GET /users/<id>` や `GET /posts` は、WP の既定の全項目を返す。§4 のとおり中継は本文を解釈しないので、そのまま通る。
- 悪用の筋道: トークンを持つ相手（漏えい時）、またはバッチの不具合で `_fields` なしの要求が出る。`/users/<id>` は数値 ID や `description`、`avatar_urls` など、`/posts` は本文全体を返す。
- 影響: どれも公開 API の範囲だが、「中継ができることはバッチが今読んでいるものを読むだけ」（180 行）が成り立たない。NFR-35 が扱わないとした項目（ユーザー ID、アバター URL）が中継を通る。本文を含むと応答が大きくなり、§4 の大きさの見込みも外れる。
- 対策: `_fields` を全パスで必須にする（欠けたら 400）。`/posts` の `status` も必須にする。一覧の `per_page` など、wp_fetch が常に送るキーも必須にできるか確かめ、できるものは「必須のキー」として表に書く。
- 根拠: ADR の記述の読み取り。WP が `_fields` なしで全項目を返すのは一般的な REST API の動作で、対象サイトでは試していない。
- 関係: NFR-35、security.md「公開するデータ」

#### M-2 プレビューのデプロイで、検査を除いた中継のコードが hnd1 で動きうる

- 対象: ADR 0011 §1（43 行）、§3（83、87 行）
- 問題: §3 の防御（トークンをプレビューに渡さない、fail closed）は、中継のコードが main のものであることが前提である。ルートディレクトリの指定から Git 連携と読めるが、未 merge のブランチや fork の PR を Vercel がプレビューにするかを ADR は定めていない。プレビューのコードは検査を外せるので、トークンは防御にならない。残る防御は Standard Protection だけで、その設定はリポジトリの外にあり、ADR でも「有効にする」と書かれているだけである。
- 悪用の筋道: 第三者が public リポジトリを fork し、`api/relay.ts` の検査と許可リストを消した PR を出す。プレビューが作られ、Standard Protection が外れている（誤操作、範囲の設定の誤り）と、任意のパス・メソッドで WP に届く中継が得られる。ビルド中にも PR のコードが動く。
- 影響: ログイン画面まで届く中継が Small Piece のチームの配下にできる。ただし、上記の前提のとおり攻撃者は自分の環境でも同様のことができると考えられ、増える損失は主にチームの実行回数と、対象サイトへの攻撃元としての名義である。
- 対策: このプロジェクトは production だけデプロイする形にする。候補は、Vercel の Ignored Build Step（または同等の設定）で main 以外のビルドを止めること。production ブランチが `main` であることも確かめる。ADR §3 に「プレビューを作らない」を決定として書き、Standard Protection はその次の層とする。設定の可否は事実票で確かめる。
- 根拠: ADR の記述の読み取り。Vercel 側の設定は未確認（確認項目 1、2）。
- 関係: security.md「fork からの PR で Secrets に触れる経路を作らない」、脅威モデル「public リポジトリを読む第三者」

#### M-3 トークンのローテーションで、古いデプロイが旧トークンを受け付け続ける可能性がある

- 対象: ADR 0011 §3（89-94 行）、未確認の事項（226 行）
- 問題: 手順は「環境変数を更新し、再デプロイする」だが、過去のデプロイの扱いがない。ADR 自身が「環境変数の更新と再デプロイの関係」を未確認としている。過去のデプロイが当時の環境変数のままで動くなら、旧トークンは次の場合に有効なまま残る。
  - 過去のデプロイの URL に届く場合（Standard Protection で閉じる前提だが、M-2 と同じ 1 層）
  - インスタントロールバックなどで過去のデプロイを production に戻した場合
- 悪用の筋道: 漏えいしたトークンを持つ相手が、無効化のあとも過去のデプロイの URL で中継を使い続ける。
- 影響: 「漏えいのときは 2 を先に行い、無効化を優先する」（94 行）の効果が確実でなくなる。
- 対策: 手順に「過去のデプロイを削除する、または旧トークンで届かないことを Vercel の設定で確かめる」を足す。ロールバックのときはトークンの再設定が要ることも書く。§3 の 93 行のとおり、旧トークンの確認のために WP へ問い合わせない方針は保つ（旧トークンがまだ有効だと、確認の要求が WP に届くため。確認は Vercel の設定とデプロイの一覧で行う）。
- 根拠: ADR の記述の読み取り。Vercel の動作は未確認（確認項目 3）。
- 関係: NFR-44、06 §3、脅威モデル「誤操作」

#### M-4 トークンが漏れたときの上限と検知がない

- 対象: ADR 0011 §3（95 行）、§5（133 行）、§7（155 行）、§8（165 行）
- 問題: 「間隔（1 秒以上）はバッチの側で保たれる」は正規のバッチにしか当てはまらない。中継は状態を持たずレート制限もないので、トークンを持つ相手は並列に WP を読める。§7 の「問い合わせの主体はバッチのまま」は、トークンが漏れていない間だけ成り立つ。さらに、`unauthorized` や想定外の件数を見る仕組みがなく、漏えいに気づく手段がない。§8 の「新しい監視は足さない」は失敗の検知についての判断で、悪用の検知は検討されていない。
- 悪用の筋道: トークンの漏えい（ログへの誤出力、運用担当の端末）のあと、`/posts?per_page=100` を並列に繰り返す。4 MB 近い応答と最大 25 秒の実行で、Vercel の実行時間を消費する。WP には 1 要求につき 1 要求が届く。
- 影響: 対象サイトの負荷（脅威モデルの資産「対象サイトへの影響」）と Vercel Pro の費用。未認証の大量要求も、WP には届かないが関数の実行回数を増やす。
- 対策: 次のいずれかを ADR に決定として書く。
  1. Vercel の Firewall のレート制限を `/api/relay` に設定する（1 日数十回の用途なので低い上限でよい）。プランの条件は事実票で確かめる。
  2. Vercel の費用の上限や通知を設定する。
  3. 上記を見送るなら、§3 の「影響」に対象サイトの負荷を明記し、中継を止める手順（環境変数を消すと 500 で全拒否になる）を漏えい時の対処に書く。

  加えて、バッチが成功している日の実行回数の目安（1 日数十回）を運用手順に書き、Vercel の使用量の画面を定期点検で見る。
- 根拠: ADR の記述の読み取り。
- 関係: NFR-72、security.md「対象サイトへの配慮」

### 低

#### L-1 著者の slug: ADR §9 の未確認は解ける。NFR-35 の範囲内だが、文言の食い違いが残る

- 対象: ADR 0011 §9（170-172 行）、未確認の事項（230 行）、.claude/rules/security.md「公開するデータ」、docs/requirements/05_non_functional.md NFR-35（55 行）
- 確認した事実（ADR が未確認としたもの）:
  - slug は保存され、公開もされる。`internal.wp_author.author_slug` が主キーで、`public.pub_author` が `author_slug` を anon に公開している（0005_public_views.sql 131-134 行）。
  - BI では文字として出さず、href に使う（apps/web/src/components/SiteLinks.tsx 26、37 行）。ただし S-02e の `<option value={item.slug}>`（apps/web/src/screens/s02/S02eScreen.tsx 169 行）と、ページのデータ（apps/web/src/lib/page-data-schema.ts 169、228、319 行）にも載る。
- 問題: NFR-35 は「表示名と著者ページの URL（slug）」と書き、「slug は WordPress では多くの場合ログイン名と同じため、著者ページへのリンク先にだけ使い、画面に文字列として出さない」と判断済みである。FR-30 も「著者 slug はサイト上で公開されており守りにならず」としている。よって ADR §9 の判断は要件の範囲内で、**新しい逸脱ではない**。一方、security.md の「表示名と著者ページの URL だけ」「ログイン名は保存もしない」には slug の断り書きがなく、slug がログイン名と同じ場合に字面では衝突する。
- 悪用の筋道: slug がログイン名と同じ場合、BI の公開データから著者のログイン名の一覧が得られる。ただし同じ値は対象サイトの著者ページの URL と `/users/<id>` の応答で公開済みであり、BI と中継で新しく開示される情報はない。
- 影響: 小さい。ブルートフォースの材料が増えるわけではない。
- 対策:
  - ADR §9 に NFR-35 と FR-30 を根拠として書き、230 行の未確認を「公開ビューと BI の href に出る。NFR-35 の範囲内」に改める。
  - security.md の該当の行に「著者ページの URL に含まれる slug は NFR-35 のとおり扱う」と足すかを依頼者が決める。
  - `<option value>` は「リンク先にだけ使う」の字面から外れる。画面の文字には出ないので実害はないが、著者ページへの移動に使うだけかを次の BI の変更時に確かめる（Grep の 1 行しか読んでいない）。
- 関係: NFR-35、FR-30

#### L-2 著者の数値 ID が Vercel を通ることが ADR に書かれていない

- 対象: ADR 0011 §5（134 行）、wp_fetch.py 4 行目（「メモリの外に出さない」）
- 問題: `/users/<id>` の ID はヘッダで中継に渡り、中継から WP への URL になる。中継のログには出さないが、Vercel の基盤が関数の外向きの要求を記録するかは ADR の未確認の項目（228 行）に含まれていない。値は WP が公開している ID で、格納の禁止（NFR-35）に当たるかは基盤の記録の有無による。
- 対策: 228 行の確認項目に「外向きの fetch の URL が基盤のログに残るか」を足す。残るなら、§5 に保持期間と受け入れの理由を書く。

#### L-3 未認証の相手への応答が、トークンの検査より先に分かれる

- 対象: ADR 0011 §3（86、87 行）、§4（117、121 行）
- 問題: 「最初にトークンを検査する。失敗なら 401」と、「GET 以外は 405」「環境変数がなければ 500」の順序が決まっていない。未認証の相手に、中継の設定の状態（500）とメソッドの制限（405）が分かる。
- 対策: 順序を「環境変数がなければ、未認証の相手にも認証済みの相手にも同じ応答」「メソッドの判定はトークンの検査のあと」と明記する。500 のかわりに 401 に揃える案もある（`outcome=misconfigured` はログで分かる。ただし、バッチの再試行は 401 で止まるので、§4 の表も直す）。

#### L-4 応答ヘッダの規則の扱いが書かれていない

- 対象: ADR 0011 §4（102 行）、security.md「BI アプリ（Vercel）」
- 問題: security.md は Vercel の BI アプリに CSP、`Referrer-Policy`、`frame-ancestors` を求めるが、中継が付けるのは `Cache-Control` と `nosniff` だけである。中継は BI アプリではないので規則違反とは言い切れないが、ADR に対象外とする理由がない。
- 対策: 固定の `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` と `Referrer-Policy: no-referrer` を足す（費用はほぼない）。足さないなら、対象外の理由を ADR に書く。

#### L-5 依存の監視と CI の対象に中継が入っていない

- 対象: ADR 0011「影響する設計文書」（191-217 行）、.github/dependabot.yml（7、18、29、39 行）
- 問題: `dependabot.yml` の対象は `/`、`/apps/batch`、`/.github/requirements`、`/apps/web` で、`/apps/wp-relay` がない。ADR の影響の表にも、`dependabot.yml`、`audit.yml`、`ci.yml` が挙がっていない。実行時の依存はゼロでも、開発時の依存とロックファイルは増える。
- 対策: 影響の表に 3 ファイルを足す。`npm audit` または `pnpm audit` の対象に `apps/wp-relay` を含める。
- 関係: security.md「依存」

#### L-6 中継の拒否と上流の拒否を、Actions のログから区別できない

- 対象: ADR 0011 §4（113、115 行）、§8（165 行）、未確認の事項（228 行）
- 問題: 上流の 401 はそのまま 401 で返るので、状態コードだけではトークンの誤りと上流の拒否を区別できない。§8 は切り分けを Vercel のログに頼るが、その保持期間は未確認である。保持が短いと、翌日に見たときに材料がない。
- 対策: 中継の 401 と上流の 401 を分ける形（列挙値の応答ヘッダ `X-Relay-Outcome` など。秘密を含まない固定値のみ）を検討する。バッチのログは現在の方針どおり kind までとし、kind に `relay_auth` などの列挙値を足す案もある。§8 に保持期間の確認を前提として書く。

#### L-7 実装のときに確かめること

設計の欠陥ではなく、ADR の文言だけでは実装が分かれる点である。

- 4 MB の上限は、本文を読み切ってからではなく、読みながら数えて打ち切る。`Content-Length` を信用しない（§4、127 行）。
- 20 秒の待ちは、応答ヘッダまでではなく本文の読み終わりまでを含める（§4、129 行）。
- `WP_RELAY_URL` の `localhost` と `127.0.0.1` の例外は、ホストの完全一致で判定する。`localhost.example.com` を通さない（§6、143 行）。
- `apps/wp-relay/api/` に `relay.ts` 以外のファイルを置かない。置いたファイルが別の関数として公開されないことを、デプロイの確認に含める（Vercel の動作は未確認）。

## 問題なしと確認した項目

文書の設計として確認した。実装での確認は別に要る。

- **SSRF**: 転送先は定数の URL に完全一致で検証したパスを連結するだけで、ホストとスキームを環境変数や入力から作らない（§2、75 行）。リダイレクトを追わない（77 行）。
- **パスの許可リスト**: 完全一致で、`/` の追加、`..`、エンコードを許さない。`/users/<id>` の正規表現は `^[1-9][0-9]{0,9}$` で、ログイン画面や `wp-admin` などには届かない。
- **クエリ**: 受信した文字列を流用せず、検証済みの組から組み立て直す（76 行）。未知のキーと重複は 400。
- **ヘッダの遮断**: 受信ヘッダ（`Authorization`、Cookie、`X-Forwarded-For`）を WP に転送しない（78 行）。上流の `Set-Cookie`、`Server`、`Location` を返さない（101 行）。
- **認証**: production に保護が効かないことを踏まえて中継の中で検査する。Bearer ヘッダで、クエリに置かない。32 バイト以上の乱数。SHA-256 のあとに `timingSafeEqual`。環境変数がないときは全拒否（fail closed）。401 は本文が空（83-87 行）。
- **トークンの置き場**: Environment `production` の Secret と Vercel の Production 環境だけ。`daily` と `backfill` のステップだけに渡す（88、140 行）。BI と環境変数を共有せず、Supabase と GA4 の認証を持たせない（43 行）。
- **バッチ側のトークンの流れ**: `follow_redirects=False` は変えないので、3xx でトークンが別のホストに送られない（wp_fetch.py 162 行）。`SecretStr` で扱う。中継の失敗時に直接接続へ切り替えない（147 行）。
- **バッチのログ**: root のレベルを `CRITICAL + 1` にしているので、`httpx` の INFO のログで `WP_RELAY_URL` が出ることはない（__main__.py 59-61 行）。
- **中継のログ**: 列挙値の `outcome`、`status`、`duration_ms` だけで、トークン、クエリの値、パスの ID、本文を出さない。列挙値なのでログへの注入もない（§5）。
- **応答の絞り込み**: 上流のヘッダのうち形を検査した 2 つだけを返す。2xx 以外の本文を返さない。`no-store`（§4）。
- **security.md「問い合わせは日次バッチだけ」**: 中継に cron、ヘルスチェック、再試行を持たせず、1 要求が WP への最大 1 要求で、BI やブラウザから呼ばない（§7）。正規の経路については整合している。トークン漏えい時は M-4。
- **能動的な問い合わせ**: 自動テストは偽の上流で行い、確認だけの問い合わせを定期的に流さない（156 行）。
- **出口 IP の前提が崩れたとき**: 失敗する側に倒れる。別経路へ切り替えず、wp_fetch の失敗では DB は変わらない（§8）。200 の別の本文で返った場合、一覧は `X-WP-TotalPages` がないと `BatchValidationError` で止まる（wp_fetch.py 199-203 行）ので、ADR 164 行の懸念は、ヘッダのない応答については既存のコードで止まる。中継が形の合わないヘッダを落としても（§4、103 行）、同じ検査で止まる。`X-WP-Total` だけがない場合は件数の検査が飛ぶ（302 行）が、`X-WP-TotalPages` がある応答に限られ、削除の上限（382-384 行）が残る。
- **選択肢の評価**: 案 D（セルフホストランナー）を public リポジトリで不採用とした判断は妥当。
