## 指摘（重要度順）

### 低-1: main ブランチに保護もルールセットもない

- 対象: GitHub リポジトリ設定（Settings > Branches、Settings > Rules）
- 問題: `branches/main/protection` は 404（Branch not protected）、`rulesets` は空。force push、ブランチ削除、直接 push を止めるものが何もない。
- 悪用の筋道: 書き込み権限を持つアカウントの認証情報が漏れる、または誤操作で main が書き換わる。将来 Workload Identity Federation の属性条件が「このリポジトリの main」を信頼する前提になるため、main に載ったものはそのまま GA4 の読み取りと Supabase の書き込みの権限で日次実行される。
- 影響: 今はドキュメントしかないので実害なし。ワークフローを置いた時点で、main の完全性が BI データの完全性と秘密情報の保護に直結する。
- 対策: ルールセットで最低限「force push の禁止」「削除の禁止」を main に設定する。PR 必須・レビュー必須にするかは、.claude/rules/git-autonomous.md の運用（Claude が main に直接 push する）との兼ね合いで依頼者が決める。.github/workflows/ を追加する前に設定する。
- 根拠: `gh api repos/takatsu-connect/access-analyzer/branches/main/protection` → 404、`gh api repos/takatsu-connect/access-analyzer/rulesets` → `[]`
- 関係する要件 ID: なし（要件定義は未着手。非機能要件に「main の保護」を入れることを推奨）

### 低-2: .gitignore に `.env` と鍵ファイルの除外パターンがない

- 対象: .gitignore:1-9
- 問題: 除外されているのは beads 関連（.dolt/、*.db、.beads-credential-key、.beads/proxieddb/、*.gate.lock*）と credentials/ だけ。`.env`、`.env.*`、`*.pem`、`*.p12`、サービスアカウントの JSON などは除外されていない。
- 悪用の筋道: 構築工程で開発者が `.env` をリポジトリ直下に置き、`git add` の対象指定を誤ってコミットする。public リポジトリなので push した瞬間に第三者が読める。
- 影響: 今はコードも `.env` も無いので実害なし。push protection が有効なので、既知の形式のトークンは push 時に止まるが、形式が登録されていない値（DB の接続文字列など）は通る。
- 対策: 構築工程の前に `.env`、`.env.*`、`!.env.example`、`*.pem`、`*.p12`、`*.key`、`*-sa.json`（または `*service*account*.json`）を追加する。CLAUDE.md の「.env.example に項目名だけ書く」方針と揃える。
- 根拠: .gitignore の全文を読んだ。`git ls-files` に該当ファイルは無い。
- 関係する要件 ID: なし

### 低-3: GitHub Actions の実行ポリシーが既定のまま

- 対象: GitHub リポジトリ設定（Settings > Actions > General）
- 問題: `allowed_actions` が `all`（マーケットプレイスのどの Action でも使える）、`sha_pinning_required` が `false`、fork からの PR のワークフロー承認が `first_time_contributors`（初回貢献者のみ承認が必要）。
- 悪用の筋道: ワークフローに書いた第三者 Action のタグが乗っ取られ、`id-token: write` を持つジョブや Secrets を扱うジョブで悪意あるコードが動く。
- 影響: 今はワークフローが無いので実害なし。
- 対策: ワークフローを追加する前に、allowed_actions を「GitHub 製と verified creators のみ」に絞り、SHA 固定を必須にし、fork PR の承認を `all_external_contributors` にする。GITHUB_TOKEN の既定権限はすでに `read` で問題ない。
- 根拠: `gh api repos/takatsu-connect/access-analyzer/actions/permissions`、同 `/workflow`、同 `/fork-pr-contributor-approval`
- 関係する要件 ID: なし

## 今後の工程で見るべき点

1. 要件定義: 公開してよいデータの許可リスト（記事、著者の表示名、カテゴリ、タグ、日付、集計値）、小さな数を伏せるしきい値、地域と流入元の粒度を非機能要件（NFR）として ID 付きで書く。非公開・下書き・パスワード付き記事の除外も要件にする。
2. 設計: Supabase の全表で RLS を有効にし、anon ロールの権限を公開用ビューの select だけ（または無し）にする。BI からの読み取りはサーバー側だけで、Vercel の環境変数に `NEXT_PUBLIC_` を付けた Supabase キーを置かない。
3. デプロイ: ワークフローの `permissions:` を最小にし、`id-token: write` は認証するジョブだけ、Action は commit SHA で固定、`pull_request_target` を使わない、ログに行データや API 応答を出さない。public リポジトリの 60 日無活動による定期実行の自動停止を運用手順に書く。WIF の属性条件を repository と `refs/heads/main` に限定する。
4. 運用: 鍵のローテーションと漏えい時の対応手順、バッチ失敗の通知を docs/operations/ に書く。
5. 初回公開前: 全観点（1〜7）で総点検を行う。
