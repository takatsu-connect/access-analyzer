## 結論

骨組み（期間の選択 → 主な数字 → 図 → 表の折りたたみ → 注記、という読む順、色を青の濃淡だけにすること、選択中の印を太字と下線でも示すこと）は良く、壊れて見える画面はない。一方で、**見出しの大きさ、リンクの色、表の列幅を、画面ごとではなくブラウザの既定値や `body` の 1 行に任せている**ため、画面ごとに見た目がばらつき、スマートフォンでは数字や見出しが不自然な位置で折れている。ほとんどは `globals.css` と共通部品の数か所を直せば全画面に効く。

最優先で直すこと 3 つ:

1. **スマートフォンでヘッダが画面の半分を占める**（`/articles` 系で h1 の上端が 407px / 780px）。`SiteHeader.module.css` の並べ方を変える（C-1）。
2. **見出しの大きさとリンクの色を globals.css で決める**。いまは S-01 だけが 24px / 18px、他の画面はブラウザ既定の 32px / 24px で、スマートフォンで「た？」「安）」だけが次の行に落ちる（C-2、C-5）。
3. **`body` の `overflow-wrap: anywhere` をやめる**。表の文字の列が 1〜2 文字幅まで縮み、「news.exa / mple」「記事 > お / 店の紹 / 介」のように折れている。スマートフォンの記事の表の値（12px）の折れも合わせて直す（C-3、C-4）。

重要度ごとの件数: 高 4 件、中 10 件、低 7 件（共通 17 件、画面ごと 4 件）。

## 共通の問題

### 高

#### C-1 スマートフォンでヘッダとデータの更新状況が画面の上半分を占める

- 画面と場所: 全画面のヘッダ（`SiteHeader`）。特に記事の画面（S-02 系、S-03）。
- いまの状態: 360px 幅で、主タブ 6 個が 2 行に折れ（「投稿活動」だけが 2 行目）、記事の画面ではさらに下位タブ 5 個が 3 行に折れる。計測ではヘッダの下端が 149px（S-01）/ 290px（記事の画面）、h1 の上端が 244px / 407px。`/articles` では最初の画面（780px）に h1 と期間のボタンしか入らず、記事は 1 本も見えない（`strip\articles-m-0.png`）。
- 問題: 開いた人がスクロールしないと「何の画面か」以外が分からない。2 行目に 1 個だけ残る「投稿活動」は、タブの一部に見えにくく、押し忘れられる。
- 直す案（`SiteHeader.module.css` だけで直す）:
  - 600px 未満で主タブを 3 列 × 2 行の格子にする。`.list { display: grid; grid-template-columns: repeat(3, 1fr); gap: 0; }`、`.link { min-height: 2.75rem; padding: var(--space-2) var(--space-1); text-align: center; font-size: var(--font-size-sm); }`。行の数は同じ 2 行だが、意図した並びに見え、6 個が同じ大きさで押せる。
  - 600px 未満で下位タブを 1 行の横スクロールにする。`.subList { flex-wrap: nowrap; overflow-x: auto; scrollbar-width: none; }`、`.subLink { white-space: nowrap; min-height: 2.75rem; }`。選んでいるタブが見えるよう、`aria-current` の要素を読み込み時に `scrollIntoView({ inline: 'center' })` で寄せる（ここは TSX の変更が要る）。これで記事の画面のヘッダは約 290px → 約 190px になる見込み。横スクロールの扱いは「依頼者に確認すること」1 に書いた。
  - `.inner` の下の余白と、データの更新状況（`DataStatus`）の上下の余白を詰める（C-9）。
- 重要度: 高

#### C-2 見出しの大きさが画面ごとに違い、スマートフォンで変な位置で折れる

- 画面と場所: 全画面の h1、h2、h3。
- いまの状態: 見出しの大きさを決めているのは `s01.module.css`（h1 = `--font-size-xl` 24px、h2 = `--font-size-lg` 18px）と `not-found.module.css`（h1 24px）だけで、他の画面はブラウザの既定値（h1 32px、h2 24px）のまま。同じ「日ごとの読まれた回数」が S-01 では 18px、S-03 では 24px（`strip\home-m-0.png` と `strip\article-101-m-0.png`）。360px 幅では「この記事はどう読まれ / た？」「どれくらい読み込まれたか（目 / 安）」「月ごとの公開本数（直近 24 か / 月）」のように最後の 1〜2 文字だけが次の行に落ちる。
- 問題: 画面を移るたびに見出しの強さが変わり、どれが画面の主題でどれが節なのかの差が画面ごとに違う。S-03 では h2（24px）が本文の数字より目立ち、一文しかない節（「到達のお知らせ」など）まで大きく見える。
- 直す案（`globals.css` に 1 か所で書き、`s01.module.css` の `.h1`、`.h2` の `font-size` と `not-found.module.css` の `.title` の `font-size` を消す）:

  ```css
  h1, h2, h3 { line-height: var(--line-height-tight); text-wrap: balance; word-break: auto-phrase; }
  h1 { margin: 0 0 var(--space-4); font-size: var(--font-size-xl); }          /* 24px */
  h2 { margin: var(--space-7) 0 var(--space-3); font-size: var(--font-size-lg); } /* 18px、節の前は 48px */
  h3 { margin: var(--space-5) 0 var(--space-2); font-size: var(--font-size-md); }
  @media (min-width: 600px) { h1 { font-size: var(--font-size-2xl); } h2 { font-size: var(--font-size-xl); } }
  ```

  `text-wrap: balance` は iOS Safari 17.5 以降と Chrome で効き、行の長さをそろえて 1 文字だけの行を防ぐ。`word-break: auto-phrase` は Chrome だけで効く（文節で折る）。どちらも効かない環境では今と同じ表示になるだけ。
- 重要度: 高

#### C-3 `body` の `overflow-wrap: anywhere` で、表の文字の列が 1〜2 文字の幅に縮む

- 画面と場所: 幅を決めていない表の全部。S-01 のリンク元のサイト、S-05 の「どのカテゴリの記事を書いたか」、S-06 の子カテゴリの表、S-08 のカテゴリの表、広い画面の記事の表（S-02e）。
- いまの状態: 「リンク元のサイ / ト」「news.exa / mple」（`strip\home-m-0.png` 4 枚目）、「記事 > / お店の紹 / 介」（`strip\author-a-m-0.png` 2〜3 枚目）、「お店の紹介」の下に 1 語ずつ縦に並ぶ（`strip\categories-m-0.png` 2 枚目）。1280px 幅の記事の表では、タイトルの列が約 130px しかなく題名が 2〜4 行に折れる一方、数の列は右に大きな空きがある（`img\articles-w-1.png`）。
- 問題: `overflow-wrap: anywhere` は、表の列幅を決めるときの最小幅（min-content）を 1 文字分にしてしまう。そのため表の自動の列幅で、文字の列が真っ先に削られ、数の列（`keep-all` で縮まない）が余りを取る。ドメインやカテゴリ名を 1 単語として読めず、行も高くなる。
- 直す案:
  - `globals.css` の `body` を `overflow-wrap: break-word;` に変える。`break-word` は、はみ出すときだけ折り、列幅の計算には影響しない。長い URL や題名のはみ出しは、これまでどおり防げる。
  - 表の文字の列に最小幅を足す。記事の表は `ArticleTable.module.css` の広い画面で `.head.title, .cell.title { min-width: 16em; }`、数の列は `.numeric { width: 1%; white-space: nowrap; }`（必要な幅だけ取る）。他の表も同じ考え方で、ラベルの列に `min-width: 8em`（ドメイン、カテゴリ）。
  - 直したあと、360px で各表を開いた状態のはみ出しを、既存の検査（`shots/shoot.mjs` の「折りたたみを開いた状態」の検査）でもう一度見る。
- 重要度: 高

#### C-4 スマートフォンの記事の表で、値が 12px で、数と単位の間で折れる

- 画面と場所: `ArticleTable`（S-02 の各一覧、S-02e、S-05 の記事の一覧、S-07b）の 600px 未満の表示。
- いまの状態: 値のセルが `--font-size-xs`（12px）で、3 つの値を等幅に並べるため 1 つ約 105px しかない。「最初の 1 か月 2 / 日目: 30 回」「最初の 1 か月 324 / 回」のように、数の途中や数と単位の間で折れる（`strip\articles-m-0.png` 2〜4 枚目）。1 行（題名・印と「記事を開く ↗」・値・「詳しく」）の高さは約 190px で、42 本の `/articles` は縦 10,029px になる。S-02「よく読まれた記事」では、いちばん大事な「この期間 1,134 回」が 12px で行の右端にあり、題名や「記事を開く ↗」より弱い（`strip\articles-top-m-0.png`）。
- 問題: 読者の 77% がスマートフォンなのに、表の主な数字がいちばん小さい文字になっている。値が折れると、どの名前の値なのかを読み違えやすい。
- 直す案（`ArticleTable.module.css` の 600px 未満と、値の名前の部品 `MaskedCell.module.css` の `.label`）:
  - 値の名前と値を 2 段にする。`.label { display: block; font-size: var(--font-size-xs); color: var(--color-text-muted); }`、値は `font-size: var(--font-size-sm); white-space: nowrap; font-variant-numeric: tabular-nums;`。名前は折れてもよいが、値と単位は折れなくなる。
  - その画面の主な値（S-02「よく読まれた記事」ならこの期間の読まれた回数、「新着記事の立ち上がり」なら最初の 1 週間）の列だけ `font-size: var(--font-size-md); font-weight: 700;` にする。どの列が主な値かは、すでに画面ごとに決まっている並べ替えの列を使えばよい（TSX で `.primary` を付ける）。
  - 行の高さを詰める: `.cell.title` の `padding-top` を `var(--space-3)`、値の行の `padding-bottom` を `var(--space-1)`、「詳しく」の行の下を `var(--space-2)` にし、「記事を開く ↗」は印と同じ行のまま（いまの形）でよい。目安は 1 行 140px 前後。
- 重要度: 高

### 中

#### C-5 リンクの色を決めていない箇所があり、ブラウザ既定の青になる

- 画面と場所: S-03 の著者名のリンク（「架空 一郎」）など、部品の CSS でクラスを付けていない `a`。
- いまの状態: 題名のリンクは `--shade-5` の濃い青なのに、隣の著者名はブラウザ既定の明るい青（`img\article-101-w-0.png`）。訪れたあとは既定の紫になる。ダークでも既定のリンク色になる。
- 問題: 同じ行の 2 つのリンクが別の種類に見える。紫は基調色以外の色で、色の方針から外れる。
- 直す案: `globals.css` に `a { color: var(--shade-5); text-underline-offset: 0.2em; } a:visited { color: var(--shade-5); }` を足す。部品ごとの `color: var(--shade-5)` はそのままでも害はないが、重複なので順に消してよい。
- 重要度: 中

#### C-6 「このページの数字について」が全画面で同じ 6 項目を出し、長い

- 画面と場所: `CommonNotes`（全画面の下、404 にも出る）。
- いまの状態: 360px 幅で高さ約 500〜550px、項目 6 つと「詳しく」2 つ。S-08（公開本数の画面）や S-06 に、その画面にない「多くの記事はこの範囲」の説明が出る。404 にも出る（`strip\notfound-m-0.png`）。上の余白が `--space-7`（48px）で、ページの最後に大きな灰色の箱が来る。
- 問題: 毎回同じ長い箱を見ると、読む人は読み飛ばすようになり、本当に必要な注記（伏せ値の「—」）まで読まれなくなる。画面にない語の説明は「どこにあるのか」と探させる。
- 直す案:
  - `CommonNotes` を既存の `Details` 部品で包み、閉じた状態で出す（`summary` は「このページの数字について」）。閉じた箱の高さは約 48px になる。
  - 画面ごとに出す項目を選べるようにする（`CommonNotes` に項目の ID の配列を渡す）。どの画面にどの項目が要るかは文言の担当（analytics-advisor）に決めてもらう。
  - 404 では出さない。
  - `.notes` の `margin-top` は `var(--space-6)` にする。
- 重要度: 中（決めごとを含むので「依頼者に確認すること」2 にも書いた）

#### C-7 押せる部品の高さが 40px 以下

- 画面と場所: 期間のボタンと月の選択（`PeriodPicker`、計測 40px）、並べ替えのボタン（`ArticleTable .button`、40px）、折りたたみの `summary`（`Details`、29〜32px）、ヘッダの題名（23px）。
- 問題: 44px 四方の目安に届かない。特に「詳しく」は記事の表に何十個も並び、ほかの行の「詳しく」と押し間違えやすい。
- 直す案: `PeriodPicker.module.css` の `.button, .select` と `ArticleTable.module.css` の `.button` を `min-height: 2.75rem`。`Details.module.css` の `.summary` を `display: flex; align-items: center; min-height: 2.75rem;`。トークンを 1 つ足して共有すると、今後もそろう: `globals.css` に `--tap-min: 2.75rem;`。
- 重要度: 中

#### C-8 折れ線の図が低く、広い画面では平らに、狭い画面では日付を押しにくい

- 画面と場所: `LineChart`（S-01、S-03、S-05 など）、`Curve`（S-03 の公開からの読まれ方）。
- いまの状態: `LineChart.tsx` の `HEIGHT = 160` 固定。1280px 幅では描画域が約 930 × 105px で、縦の変化がほとんど見えない（`img\home-w-0.png`）。360px 幅では 28 日分が約 312px に並び、1 日あたり約 11px で、狙った日をタップしにくい。凡例が、固定行の文（「11 月 3 日: 読まれた回数 281 …」）の下にあり、図から離れている。目盛りの文字は 11px。
- 問題: 変化を見るための図なのに、広い画面で変化が読めない。凡例が図の直下にないため、点線が何かを探す。
- 直す案:
  - 図の高さを CSS で決める（SVG の `height` 属性より CSS が優先される）。`LineChart.module.css` の `.svg { height: 12.5rem; }`、`@media (min-width: 600px) { .svg { height: 16rem; } }`。`Curve.module.css` も同じ値にする。座標の計算が `HEIGHT` 定数に依存しているなら、`viewBox` と `preserveAspectRatio="none"` を使わず、定数を 2 つ（狭い・広い）持つ形に直す（担当の判断）。
  - 並びを「図 → 凡例 → 固定行 → タップの案内」にする。凡例は図のすぐ下に置く。
  - 目盛りの文字を `11px` → `12px`（`LineChart.module.css` 67 行、`Curve.module.css` 59 行、`Heatmap.module.css` 47・84 行）。
  - タップの判定幅を、点の幅ではなく日ごとの列全体（いまの実装がそうなら、そのまま）にし、図の左右の矢印キーで日を動かせることを、タップの案内の文に添える（キーボードの利用者向け）。
- 重要度: 中

#### C-9 データの更新状況と h1 の間が広い

- 画面と場所: `DataStatus` と `layout.module.css` の `main`。
- いまの状態: 1280px 幅で、更新状況の文の下から h1 まで約 70px、360px 幅で約 40〜50px（`img\articles-w-0.png`）。S-01 だけ詰まっていて、画面によって h1 の位置が違う（S-01 の h1 は 24px で上の余白も小さい）。
- 問題: 更新状況の文が h1 から離れ、ヘッダの一部に見える。スマートフォンでは C-1 と合わせて最初の画面を削っている。
- 直す案: `main` の上の余白を `var(--space-5)`（24px）にそろえ、h1 の上の余白は C-2 のとおり 0 にする。S-01 の `s01.module.css` で別に持っている余白は消す。
- 重要度: 中

#### C-10 前の期間（去年の同じ月）を示す「細い枠」が、今の棒に隠れて見えない

- 画面と場所: `HBar`（S-01 の読者はどこから来たか、など）、S-08 の月ごとの公開本数。
- いまの状態: 前の値の枠は、今の棒より短いと塗りの中に隠れる。S-08 では 24 か月のうち枠が見えたのは 1 か月だけ（`strip\activity-m-0.png` 2 枚目、2026 年 8 月）。凡例は「細い枠: 去年の同じ月の本数」と説明している。
- 問題: 凡例で約束したものが図にないので、読む人は「枠がない＝去年は 0」と誤読する。
- 直す案: 枠の代わりに、前の値の位置に縦の印（幅 2px、棒より上下に 3px ずつはみ出す線、色 `--color-text`）を描く。今の棒より短くても長くても見える。凡例も「縦の線: 前の期間」に変える（文言は analytics-advisor に確認）。`HBar.tsx` の `compare` の矩形を線に替え、`HBar.module.css` の `.compare` を `stroke: var(--color-text); stroke-width: 2;` にする。S-08 の部品も同じ形にする。
- 重要度: 中

#### C-11 ダークで、選んでいる期間と棒の地が見分けにくい

- 画面と場所: `PeriodPicker` と並べ替えのボタンの選択中、`HBar` と `MiniBar` の地の棒（track）。ダークのとき。
- いまの状態: 選択中の背景 `--shade-1`（#14273c）が背景 #0f1419 とほとんど同じで、差は太字と下の 3px の線だけ（`img\home-wd-0.png`）。棒の地は背景にほぼ溶ける（`strip\home-md-0.png` 3 枚目）。
- 問題: ライトでは選択中がはっきり分かるのに、ダークでは注意して見ないと分からない。地の棒が見えないと、棒の長さが「全体の何割か」を読めない。
- 直す案: ダークの `--shade-1` は背景用に残し、選択中の背景だけ `--shade-2`（#214772）にする（`PeriodPicker.module.css` と `ArticleTable.module.css` に `@media (prefers-color-scheme: dark) { .button[aria-pressed='true'] { background: var(--shade-2); } }`）。地の棒は、ダークでは `--color-border`（#30363d）にする。選択中の下の線は両方の配色で 3px → 4px。
- 重要度: 中

#### C-12 一文しかない「まだ出ません」の節が、大きな見出しつきで並ぶ

- 画面と場所: S-03（`/articles/101`、`/articles/104`）の「到達のお知らせ」「（著者）さんのこれまでの記事と比べて」「リンク元のサイト」、S-05 の「いま読まれている記事」。
- いまの状態: 24px の h2 のあとに 1 文（「公開から 30 日たつと出ます」など）だけがあり、公開から日の浅い記事では、画面の半分近くがこうした節になる（`strip\article-101-m-0.png`）。
- 問題: 見出しの強さに対して中身がなく、スクロールしても数字が出てこない。本当にある数字（日ごとの読まれた回数、どこから来たか）が下に押しやられる。
- 直す案: C-2 で h2 を小さくしたうえで、空の状態の文は `font-size: var(--font-size-sm); color: var(--color-text-muted);` にそろえる（空の状態の部品が 1 つにまとまっていれば、そこで決める。なければ `Notice.module.css` に `.empty` を作って使う）。さらに、空の節は画面の下（「どんな端末で読まれたか」のあと）に回すか、まとめて「公開から日がたつと出る数字」という 1 つの節にすることを検討する（並べ替えは画面設計の変更なので、依頼者と architect の判断）。
- 重要度: 中

#### C-13 「記事を開く ↗」と広い画面の「↗」が、斜線に見える

- 画面と場所: `ArticleTable` の `.external`、S-03 の題名の横。
- いまの状態: Windows の既定のフォントでは「↗」が細い斜線「／」に見え、広い画面の表では題名の右の独立した列に置かれている（`img\articles-w-1.png`）。
- 問題: 押せるリンクに見えず、区切りの記号や罫線の一部に見える。広い画面では押す範囲が 24px 四方しかない。
- 直す案: 広い画面でも文字を付ける（「開く ↗」）か、矢印を SVG のアイコン（`aria-hidden`、リンクの名前は既存の読み上げ用の文のまま）にして 16px で描く。押す範囲は `.external { min-width: 2.75rem; min-height: 2.75rem; display: inline-flex; align-items: center; justify-content: center; }`。
- 重要度: 中

#### C-14 小さい文字（12px）が注記・表の見出し・凡例に多い

- 画面と場所: `KpiCard` の注記、`HBar` の「前: 41%」、表の見出し（`.head`）、S-06 の子カテゴリの表の値。

- 問題: 年配の読者には読みにくい。特に値が 12px なのは表の役割に反する。
- 直す案: 値は 14px（`--font-size-sm`）を下限にする（S-06 の子カテゴリの表、`parts.module.css`）。注記と表の見出しは 12px のままでよいが、色は `--color-text-muted`（白地で 6.3:1、足りている）を維持する。図の目盛りは C-8 のとおり 12px。
- 重要度: 低

#### C-15 KPI カードが、スマートフォンで 1 枚ずつ縦に並ぶ

- 画面と場所: S-01 の主な数字（`KpiCard`）。
- いまの状態: 360px 幅で 1 枚が約 150px、3 枚で約 470px。最初の画面に見えるのは「読まれた回数」の 1 枚だけ（`strip\home-m-0.png`）。
- 問題: 主な数字が 3 つあることが、最初の画面で分からない。
- 直す案: 600px 未満で、1 枚目（読まれた回数）は全幅、2・3 枚目は 2 列（`grid-template-columns: 1fr 1fr`）にし、2・3 枚目の値は `--font-size-xl`（24px）、注記は折りたたまずに 12px のまま。直すのは S-01 の並べ方（`s01.module.css`）で、`KpiCard` には大きさの変種（`.compact`）を足す。

#### C-16 公開した日の点が、目盛りの文字と同じ行の上にあり、何の点か分かりにくい

- 問題: 軸の外の灰色の点は、凡例を読むまで意味が分からず、目盛りの一部に見える。
- 直す案: 点の色を `--shade-4` にし、凡例の「● 公開した日」も同じ色にそろえる。凡例は C-8 のとおり図の直下に置く。

#### C-17 フォーカスの輪が、選択中のボタンの枠と重なる

- 画面と場所: `globals.css` の `:focus-visible`。
- いまの状態: 2px の `--shade-5`、オフセット 2px。白地ではよく見える（`img\x-focus-9.png`）。選択中のボタン（枠も `--shade-5`）では、輪と枠が近い色と太さで並び、どちらにフォーカスがあるか一瞬迷う。

## 良いところ（変えないでほしいこと）

- 期間の選択、主な数字、図、「同じ数字を表で見る」の順が全画面で同じで、一度覚えれば他の画面も読める。
- 選択中の印（太字と下の線）、現在のタブの印、▲▼の文字で、色だけに頼っていない。
- S-03 の「ここから下は、選んだ期間の数字です」の区切りは、期間に依存しない数字と依存する数字を分けていて分かりやすい。
- スキップリンクがあり、Tab で最初に出る。フォーカスの輪がはっきりしている。
- 図をタップすると固定行が変わり、図の下の文で値を読める（ツールチップを使わない方針どおり）。
- 色が青の濃淡とグレーだけで、評価の色がない。白地の文字のコントラストは足りている。

## 方針への意見

1. **ヘッダの横スクロール**: 「横スクロールは月ごと × カテゴリ（子カテゴリ）だけ」は表についての決まりと読めるが、ナビゲーションにも及ぶなら、C-1 の下位タブの横スクロールは使えない。その場合の代案は、600px 未満で下位タブを `select`（「記事の見方: よく読まれた記事 ▼」）に替えること。1 行 44px で済むが、どんな見方があるかが一覧で見えなくなる。横スクロール（タブの右端を薄くして続きがあると示す）のほうが、選べるものが見えるので良いと考える。
2. **共通の注記を毎回すべて出すこと**: 誤読を防ぐための注記は大事だが、同じ長い箱を毎画面で出すと読まれなくなる。画面ごとに必要な項目だけを出し、閉じた状態で置くほうが、結果として読まれると考える（C-6）。

## 依頼者に確認すること

1. スマートフォンで、記事の画面の下位タブ（よく読まれた記事 など 5 つ）を **1 行の横スクロール** にしてよいか。だめなら `select` に替える案にする（方針への意見 1、C-1）。
2. 「このページの数字について」を **閉じた状態** で出し、**画面ごとに項目を選ぶ** 形にしてよいか。よければ、どの画面にどの項目を出すかを analytics-advisor に決めてもらう必要がある（C-6）。
3. 前の期間の印を「細い枠」から「縦の線」に変えてよいか。凡例の文言が変わる（C-10）。
4. S-03 で、まだ出ない節（到達のお知らせ、これまでの記事との比較、リンク元のサイト）を画面の下にまとめてよいか。画面設計（05_screens.md）の並びの変更になる（C-12）。
