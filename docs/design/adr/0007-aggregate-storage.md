# ADR 0007: 集計の持ち方（事前集計表 + 公開ビュー、期間の表現、集計の実行場所）

- 状態: 確定（2026-11-04。依頼者の確認済み。実装時の確認項目は ADR 0009 にある）
- 更新日: 2026-11-04

- 変更履歴:

## 文脈

- 05 §4.1 の表は「何を、どの粒度で、伏せ値を付けて格納するか」を定める。設計では (1) 期間（移動窓・月・確定した暦月・公開後 30 日時点）を表にどう持つか、(2) 集計と伏せ値をどこで計算するか（バッチの Python か、Postgres の SQL か）、(3) anon に見せる形（表か、ビューか）、(4) GA4 の割当と Supabase の容量に収まるか、を決める必要がある。
- 要件の特徴: 記事 × 内訳軸 は「期間ごとに GA4 から集計済みの値を取得」する（日単位では格納しない）ので、GA4 への問い合わせは期間単位になる。合計・累積は伏せる前の値から計算する。著者・カテゴリ・タグの合計は記事の期間合計から導ける。
- 規模: 記事 300、著者 21、日 400 → 記事 × 日 は約 10 万行。期間は移動窓 6 + 月 14（毎月 +1）。

## 選択肢

### (1) 期間の表現

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A（採用） | `period` 表に期間を 1 行ずつ（移動窓は固定 ID 6 つ、日付範囲を毎日更新。月は `mYYYY-MM`）。期間別表は `period_id` で参照 | 期間の種類が増えても表の形が変わらない。移動窓の履歴を持たず上書きするので、日次差分からの復元を助けない（ADR 0003 判断 3）。BI は `period` を読んで日付範囲を表示できる |
| B | 期間別表に `start_date`、`end_date` を直接持つ | 同じ期間の重複定義や、移動窓の履歴が溜まるのを防ぐ仕組みが別に要る |
| C | 期間別表を持たず、日別表から BI（ビルド時）が期間集計する | 記事 × 内訳軸 は日別に格納できない（05 §4.1）ので、GA4 から期間ごとに取る値の置き場所がなくなる。不可 |

### (2) 集計と伏せ値の実行場所

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A（採用） | GA4 から取った期間値の正規化・伏せ値・二次伏せ・著者別の合算と、派生指標（累積、M-22〜M-24）はバッチの Python（`apps/batch`、単体テスト）。分布と帯は後の再確認 N-1 で公開ビューに移した（ADR 0003 判断 4）。記事の期間合計から導ける著者・カテゴリ・タグ・公開本数の合計は公開ビューの SQL | 規則が Python の 1 か所に集まり単体テストしやすい。ビューの SQL は合計と結合だけで単純。著者・カテゴリ・タグの合計をビューで計算しておけば、除外を追加する場合（ADR 0005 保留）もビューの変更で済む |
| B | すべて SQL（Postgres 関数を rpc で呼ぶ） | 伏せ値・二次伏せ・分位点・判定の規則を SQL に書くとテストが重い（Supabase のローカル環境が要る）。バッチ側の型と二重になる |
| C | すべて Python（著者・カテゴリ・タグの合計も表に書く） | 記事の期間合計から導ける値のために表が増える。除外を追加する場合（ADR 0005 保留）に、バッチが除外リストを読むことになる |

### (3) anon に見せる形

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A（採用） | 内部表 + 公開ビュー（`pub_*`、所有者権限で内部表を読む）。anon はビューの select だけ | 公開する列を 1 か所で統制。伏せ値の `_mask` 列の非公開もビューで表現。内部表の列を増やしても公開範囲は変わらない |
| B | 公開用の表をバッチが別に書き、anon に select を許す | 表が倍になる。「公開表に生の値を書いてしまう」実装ミスが公開に直結する |
| C | `security_invoker = true` のビュー + 内部表に anon の select ポリシー | anon が内部表の列（`_mask` など）を直接読めるようになる。列単位の grant で防げるが複雑 |

## 決定

(1) A、(2) A、(3) A。

- `period` 表で期間を表し、移動窓は上書き、月は確定後に固定、確定した暦月の参照元・市別と記事の公開後 30 日時点は 1 回だけ書く（02 §2.2、03 §3）。
- 正規化・伏せ値・派生指標はバッチの Python。合計の結合は公開ビューの SQL。
- 内部表は RLS + grant なし。公開ビューは既定（所有者権限）で作り、anon に select を grant。Supabase のアドバイザの「security definer view」警告は意図したものとして受け入れ、security-auditor のレビューで確認する。
- バッチの書き込みは psycopg で shared pooler の session mode に接続し、専用ロール `batch_writer` で upsert する（ADR 0009。前回の「supabase-js の upsert、直接接続は使わない」を置き換える）。

## 結果

- GA4 の割当: 通常日 約 30 リクエスト・約 450 トークン、バックフィル 約 310 リクエスト・約 5,000 トークン（03 §11）。1 日 200,000、1 時間 14,000 に対して十分小さい。移動窓を毎日取り直す設計でも割当に余裕がある。
- Supabase の容量: 数年で 100 MB 未満（02 §7）。Free の 500 MB に収まる。
- 再計算のコスト: 移動窓と当月・前月の期間値を毎日取り直す（GA4 約 25 リクエスト）。日別表からの再集計はビュー（ビルド時）で行い、GA4 を使わない。
- 引き受ける点: 公開ビューの SQL（特に `pub_category_period` の親行の distinct の数え方、`pub_article_cumulative` の窓関数）は結合テストで値を確かめる。ビューの列が公開範囲なので、ビューの変更は NFR-39 の手順で統制する。バッチの Python はメモリ上で生値を扱うので、ログに出さない規律（03 §15）を守る。
