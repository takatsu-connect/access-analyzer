# ADR 0006: BI の配信方式（ビルド時生成 + Deploy Hook による日次再ビルド）

- 状態: 確定（2026-11-04。依頼者の確認済み。実装時の確認項目は ADR 0009 にある）
- 更新日: 2026-11-04
- 関係: NFR-10、NFR-11、NFR-12、NFR-42、NFR-90、NFR-91、FR-02、FR-06、01_tech_stack.md §5、06_security.md

## 文脈

- データは日次でしか変わらない。ページはキャッシュして配信し、リクエストごとに Supabase に問い合わせない（NFR-11）。
- Supabase はブラウザからではなくサーバー側から読む（NFR-42）。
- Vercel Hobby（Function 呼び出し 100 万 / 月、Active CPU 4 時間、デプロイ 1 日 100 回）。
- 同時利用者は 10 人程度（NFR-12）。初期表示 3 秒以内（NFR-10）。
- 変更履歴:
  - 2026-11-04: 著者の除外（FR-36）を初回対象外にしたため、除外の記述を外した。配信方式の判断は変わらない
- URL で表示状態を共有できる（FR-06）。期間（直近 7 / 28 / 90 日、月別）とフィルタは URL に反映する。
- 存在しない記事・著者を URL で直接指定したときは 404（FR-06、FR-23、FR-30）。

## 選択肢

| 案 | 生成のタイミング | Supabase を読む場所 | 更新の仕組み |
| --- | --- | --- | --- |
| A（採用） | ビルド時に全ページを静的生成（SSG）。実体（記事・著者・カテゴリ・タグ）ごとに 1 ページ、期間は埋め込んだデータをクライアントで切り替える | ビルド時だけ（anon） | バッチの最後に Deploy Hook を呼んで再ビルド。手動の再ビルドも Deploy Hook |
| B | ISR（Incremental Static Regeneration）。初回アクセス時に生成し、タグで無効化 | 実行時（サーバー関数、anon） | バッチの最後に再検証エンドポイント（秘密トークン付き）を呼んで `revalidateTag`。時間ベースの再検証を保険に |
| C | SSG で、期間ごとにもページを分ける（記事 × 期間 = 1 ページ） | ビルド時だけ | A と同じ |
| D | SSR（毎リクエストでサーバーが Supabase を読む）+ CDN キャッシュヘッダ | 実行時 | キャッシュヘッダの TTL。無効化は Vercel の purge API |

## 比較

| 観点 | A: SSG（実体ごと） | B: ISR | C: SSG（期間ごと） | D: SSR + CDN |
| --- | --- | --- | --- | --- |
| 実行時のサーバー処理 | なし | あり（再生成時、再検証 API） | なし | 毎リクエスト |
| Supabase への読み出し | ビルド 1 回あたり約 30 クエリ | ページごとの再生成時 | ビルド 1 回あたり約 30 クエリ | リクエストごと（NFR-11 に反する） |
| 攻撃面 | 静的ファイルのみ。入力はクライアント側 | 再検証 API に秘密が要る。サーバー関数にエラー応答の規律（NFR-91）が要る | A と同じ | サーバー関数全般 |
| ページ数 | 300〜350 | 同じ（遅延生成） | 記事 225 × 期間約 20 = 4,500 以上。月が増えると増え続け、ビルドが長くなる | ― |
| ページの重さ | 記事詳細に全期間ぶんのデータ（約 20 期間 × 13 区分 + 日別 90〜400 行）を埋め込む。10〜50 KB 程度 | 期間ごとに生成すれば軽い | 軽い | 軽い |
| データ変更の反映 | 再ビルド（数分）で全ページが作り直される。古いページは残らない | `revalidateTag` で全タグを無効化。無効化漏れのリスクがある。stale-while-revalidate で 1 回は古いページが出る | A と同じ | purge の確実性に依存 |
| 「存在しない」と同じ応答 | `dynamicParams = false` で 404 | `notFound()` を実装する。生成済みページの削除は無効化で | A と同じ | 実装する |
| バッチ失敗時 | 前回のビルドが残る（NFR-90） | 前回のページが残る | A と同じ | Supabase の最新を読むので実行記録で判定が要る |
| Hobby の枠 | ビルド 1 日 1 回（デプロイ 100 回 / 日の枠内）。Function 使用なし | Function 呼び出しが発生（枠内に収まる見込み） | ビルドが長い（ビルド時間の上限は事実票にない。Q-34） | Function 呼び出しが多い |
| 実装の単純さ | 高い。データ取得はビルド時の 1 モジュールに集まる | 再検証 API、タグ設計、秘密の管理が増える | A と同じだが `generateStaticParams` が巨大 | 低い |

## 決定

案 A。

- Next.js App Router、すべてのページを `generateStaticParams` で静的生成、`dynamicParams = false`。Route Handler、Server Actions、Middleware を作らない。
- ページの単位は実体: `/`（全体）、`/articles`（一覧・検索）、`/articles/[postId]`、`/authors`、`/authors/[slug]`、`/categories`、`/categories/[id]`、`/tags/[id]`、`/activity`（投稿活動）、`/reactions`（反応指標。FR-61 を含めるとき）。パスの詳細は 05_screens.md（2 回目）。
- 期間（直近 7 / 28 / 90 日、月別）、フィルタ、並べ替えはクエリ文字列に持ち、クライアント側でページに埋め込んだデータを切り替える。埋め込むのはそのページの実体に関する全期間ぶんの公開ビューの行（移動窓 6 + 全月）。
- バッチの `publish` 工程が Vercel の Deploy Hook を POST して再ビルドする。設定変更後などの再ビルドは `publish_only` で同じ Hook を呼ぶ（03 §2）。
- ビルド時のデータ読み出しは `apps/web/src/data/` の 1 モジュールに集め、`pub_*` 以外を読まない（lint で `from('pub_')` 以外のテーブル名を禁止する）。
- FR-02 の「更新が遅れています」は、ビルド時の `pub_meta.base_date` と、クライアント側の現在日付の比較（3 日以上古い）で出す（03 §12。ワークフロー停止でビルドも止まる場合に備える）。

## 結果

- 良い点: 実行時のサーバーがなく、Supabase を読むのはビルド時だけ。公開ビューに載っているものだけが HTML / JSON に載る。失敗時は前回のビルドが残る。データの反映は全ページの作り直しで確実。
- 引き受ける点: 記事詳細ページが全期間ぶんのデータを含むので、ページが数十 KB になる（スマホでも 3 秒以内に収まる見込み。05_screens.md で埋め込む列を絞る）。月が増えるとページが少しずつ重くなる（年 12 期間分。許容）。ビルドが毎日走る（2〜3 分。Hobby のビルド時間の上限は Q-34 で確認）。ビルド失敗の通知を運用担当が受ける（Vercel のメール）。
- 将来: ページが重くなりすぎたら、期間を「移動窓 3 + 直近 24 か月」に絞る、または ISR（案 B）に移行する。`apps/web/src/data/` に読み出しが集まっているので移行の影響は限定的。
- 選ばなかった案 C は、ビルド時間が月ごとに増え続け、Hobby の枠を見ながら運用することになるため採らない。
