- §4「公開してよいデータの規則」と §5「秘密情報とアクセス経路」は .claude/rules/security.md を原本とし、要件として ID を付けて参照できる形にしたもの。両者が食い違ったら security.md を正とし、本文書を直す。

## 1. 更新頻度と鮮度（NFR-01〜NFR-04）

| ID | 要件 | 仮置き / 未確定 |
| --- | --- | --- |
| NFR-01 | データは 1 日 1 回更新する（日次バッチ、FR-70）。それより高い頻度は要求しない | ― |
| NFR-02 | 前日（基準日）までのデータが、翌日の T 時（JST）までに BI で見られる。GA4 の日次データはプロパティのタイムゾーンで 15:30 に揃うため、バッチはそれ以降に動かす | 仮: T = 18:00（Q-13） |
| NFR-03 | GA4 の遅延データ（最大 7 日）を反映するため、直近 7 日分を毎回取り直す（FR-71）。確定前の値は変わり得ることを BI に注記する（FR-02） | ― |
| NFR-04 | リアルタイムの値（当日分、GA4 のリアルタイム レポート）は取得も表示もしない | ― |

| ID | 要件 | 仮置き / 未確定 |

## 4. 公開してよいデータの規則（NFR-30〜NFR-39）

原本: .claude/rules/security.md「公開するデータ」。docs/security/audits/2026-11-03-initial.md の指摘（要件で ID を付けること）に対応する。

| ID | 要件 | 仮置き / 未確定 |
| --- | --- | --- |
| NFR-30 | 公開するのは集計値だけ。個別の訪問、個別のユーザー、個別のイベントの行は格納も表示もしない | ― |
| NFR-31 | 集計値を切る次元は次に限る: 記事、著者の表示名、カテゴリ、タグ、日付（日・曜日・時間帯を含む）、デバイス種別、流入チャネル、参照元ドメイン、地域（都道府県と市区まで）。この一覧にない次元を足すときは、要件に ID を付けて追加し、security-auditor のレビューを受ける（NFR-39） | ― |
| NFR-32 | 次のものは取得も格納も表示もしない: ユーザー ID、クライアント ID、完全な参照 URL、サイト内検索語、フォームの送信内容（問い合わせ送信数を含む、FR-63）、IP アドレス、市区より細かい地域、リアルタイムの値 | ― |
| NFR-33 | 細かい次元で切った集計値がしきい値 T 未満のとき、格納時に「T 未満」を示す値に置き換える（伏せ値）。読み出し側で丸めて済ませない。比率（エンゲージメント率など）は分母が T 未満のとき伏せる。合計値は伏せる前の値から別に計算して格納する。T は設定値として外に出し、変更はコミットで記録する | 仮: T は未確定（Q-02）。設計では設定値として扱う |
| NFR-34 | BI に含める記事は、WP REST API が公開している公開状態（publish）の投稿だけ。非公開、下書き、パスワード付きは含めない。削除・非公開化された記事は次のバッチで、関連する集計値とともに BI から消す（FR-72） | ― |
| NFR-35 | 著者について格納・表示するのは、サイトが公開している表示名と著者ページの URL（slug）だけ。メール、ログイン名、WordPress のユーザー ID は格納しない（ユーザー ID は取り込み時の結合にだけ使う）。アバター画像を使うかは未確定 | 仮: アバターは使わない |
| NFR-36 | ライター同士の順位表（著者を数値で並べた表）は、運営が許可した場合だけ出す（FR-35）。既定は全体の分布（中央値、四分位）との比較（FR-31）。著者別の公開本数（FR-51）が順位表に当たるかは未確定 | 仮: 順位表は出さない。公開本数は出す（Q-03） |
| NFR-37 | 地域の粒度は都道府県と市区まで。GA4 の city が市のレベルのため、実際には市まで。区以下は出さない | Q-11 |
| NFR-38 | 流入元は、流入チャネル（5 区分）と参照元ドメイン（sessionSource）まで。完全な参照 URL（pageReferrer）は取得しない | ― |
| NFR-39 | NFR-31 の次元、NFR-32 の除外、NFR-33 のしきい値を変えるときは、要件を更新し、ADR に理由を書き、security-auditor のレビューを受けてから実装する | ― |

## 5. 秘密情報とアクセス経路（NFR-40〜NFR-44）

原本: .claude/rules/security.md「秘密情報」「Supabase」「GitHub Actions」。設計・運用の規則だが、要件から参照できるよう ID を付ける。

| ID | 要件 | 仮置き / 未確定 |
| --- | --- | --- |
| NFR-40 | 鍵、トークン、パスワード、GA4 のプロパティ ID はリポジトリに置かない。渡す経路は GitHub Actions の Secrets と Vercel の環境変数だけ。.env.example には項目名だけを書く。リポジトリは public である | ― |
| NFR-41 | GA4 Data API の認証は Workload Identity Federation で行い、サービスアカウントの JSON 鍵を作らない | ― |
| NFR-42 | Supabase への読み書きはサーバー側（GitHub Actions と Vercel のサーバー）だけ。ブラウザから Supabase に直接アクセスしない。ブラウザに渡る名前の環境変数に Supabase のキーを入れない | ― |
| NFR-43 | Supabase の全表で RLS を有効にし、anon ロールには公開用のビューまたは表に対する select 以外の権限を与えない。書き込みは service role だけ | ― |
| NFR-44 | GitHub Actions のログ、通知（FR-74）、実行記録（FR-76）、エラー画面に、API の応答、行データ、トークン、内部 URL、スタックトレースを出さない。出すのは件数、所要時間、エラーの種別まで | ― |

## 6. データ保持（NFR-50〜NFR-52）

| ID | 要件 | 仮置き / 未確定 |
| --- | --- | --- |
| NFR-50 | Supabase に格納した集計値は全期間保持する。取り込みの開始日は依頼者の指定による | 仮: 全期間。開始日は Q-05 |
| NFR-51 | 一度取り込んだ集計値は、GA4 側のデータ保持期間の設定に依存せず Supabase に残す。GA4 側で見られなくなっても BI では見られる | ― |
| NFR-52 | 削除・非公開化された記事の集計値は、次のバッチで削除する（NFR-34）。非表示を申し出た著者（FR-36）の扱いは、著者の表示を止めるだけで集計値は残す（全体の値を変えないため） | Q-03 |

## 8. 運用負荷（NFR-70〜NFR-73）

| ID | 要件 | 仮置き / 未確定 |
| --- | --- | --- |
| NFR-70 | 通常時は無人で運用し、人が動くのは失敗の通知（FR-74）を受けたときだけ。失敗の原因が分かる程度の記録を残す（NFR-44 の範囲で） | 通知先は Q-12 |
| NFR-71 | public リポジトリの定期実行は 60 日間コミットなどの活動がないと止まる。止まらないようにする仕組み、または止まったことに気づく仕組みを用意し、運用手順に書く（D-07） | ― |
| NFR-72 | 対象サイト（takatsu-connect.com）への WP REST API の問い合わせは日次バッチだけ。間隔を空け、必要な記事だけを差分で取る。対象サイトと本番の BI にスキャンや負荷試験などの能動的な試験をしない。対象サイトの WordPress を変更する操作は、依頼者の確認なしに行わない | ― |
| NFR-73 | Supabase のスキーマ変更はマイグレーションファイルで行いリポジトリに入れる。設定（しきい値、除外する著者、順位表の有効化）の変更もリポジトリ経由で行い、履歴が残るようにする | ― |
