## 2. DS-01 GA4 Data API

### 2.1 概要

- 対象サイトは GA4 の gtag.js（測定 ID G-79CFGF83VT）で計測している。本 BI の主なデータソース。
- プロパティ ID（数字）は依頼者が控えている。リポジトリには置かず、GitHub Actions の Secrets で渡す（NFR-40）。

### 2.2 取得方法

- 日次バッチ（GitHub Actions）から Data API のレポート取得を呼び、日別の集計値を Supabase に格納する。
- 取得する次元と指標は §2.4 の範囲に限る。それ以外（特に §2.5）は取得しない。
- 直近 7 日分は毎回取り直して上書きする（GA4 の遅延データ対策、FR-71）。
- 初回は過去分をまとめて取り込む（FR-75）。開始日は Q-05。

### 2.3 認証と権限

- 認証は Workload Identity Federation（鍵なし）。サービスアカウントの JSON 鍵は作らない（NFR-41）。
- サービスアカウントには GA4 プロパティの閲覧者権限が付与済み（2026-11-03 時点）。
- 設計で確認: WIF の属性条件を repository と refs/heads/main に限定する（docs/security/audits/2026-11-03-initial.md の指摘）。

### 2.5 取得しない次元

- pageReferrer（完全な参照 URL）。参照元は sessionSource のドメインまで（NFR-38）。
- ユーザー ID、クライアント ID、ユーザー プロパティ、サイト内検索語（searchTerm 系）、フォーム送信内容、IP アドレスに関わるもの。
- city より細かい地域。
- リアルタイム レポート（Realtime API）。

### 2.6 制約

- データの確定: 日次データの処理は通常 12 時間、24〜48 時間かかることがあり、その間は値が変わる。遅れて届くデータは最大 7 日。日次データはプロパティのタイムゾーンで 15:30 に揃う。したがってバッチは 15:30 以降に動かし（FR-70、NFR-02）、直近 7 日を毎回取り直す（FR-71）。
- ユーザー数（activeUsers、totalUsers、newUsers）は日別の値を足しても期間のユニーク数にならない。期間の値が要るなら期間単位で問い合わせる（D-06）。
- 割当（1 日あたりのトークン数、同時リクエスト数）は未確認。設計で確認し、日次バッチの必要量が収まることを確かめる（D-01、NFR-61）。
- GA4 の導入時期、データ保持期間の設定は未確認（Q-05）。Data API で過去どこまで取れるかもそこで確定する。
- プロパティのタイムゾーンは未確認（Q-07）。
- city の粒度は日本では市のレベル（例: 川崎市）と見込む。区は取れないと考える（Q-11）。
- 著者やカテゴリをカスタム次元として送っているかは未確認（Q-25）。送っていなくても pagePath の記事 ID で結合できる。
- Search Console との連携の有無は未確認（Q-09）。

### 2.7 個人情報

- 取得するのは集計値だけ。§2.5 の次元を取らないことで、個人を特定できる情報を取り込まない。
- 細かい次元で切った小さな値は格納時に伏せる（NFR-33）。

## 3. DS-02 WP REST API

### 3.1 概要

- /wp-json/wp/v2/ が公開されている。認証不要。記事のメタデータの取得元。
- WP REST API には takatsu/v1、tc/v1、takatsu-bot/v1、mcp、members/v1、wp-ulike/v1、wp-analytify/v1 などサイト独自や他プラグインの名前空間があるが、本 BI が使うのは wp/v2 だけ（2026-11-03 確認）。
- Analytify プラグイン（wp-analytify/v1）が入っており、運営者は WordPress の管理画面で GA4 の数字を見てきた可能性がある（Q-32）。本 BI はこれを読まず、GA4 Data API から直接取る。
- 公開されている範囲（公開状態 publish の投稿）が BI の範囲になる。下書き、非公開は API に出ないため BI にも入らない。パスワード付きの投稿は status が publish のまま content.protected = true で API に出るため、取り込み時に除く（NFR-34、FR-72。監査 M-3）。2026-11-03 に全 225 本を確認した結果、status は publish のみで content.protected = true の記事は 0 本（D-13）。

### 3.2 取得するエンドポイントと項目

| エンドポイント | 取得する項目 | 使う指標 ID | 備考 |
| --- | --- | --- | --- |
| /wp-json/wp/v2/posts | id、date（サイトのタイムゾーン）、link（https://takatsu-connect.com/<id>/）、title、author（数値 ID。結合にだけ使い、保存しない）、categories（ID 配列）、tags（ID 配列） | M-18〜M-27、M-30〜M-34、記事属性 | `_embed=author` で著者の name、slug、link（著者ページ）、avatar_urls が付く。avatar_urls は保存しない（仮。表示に使うなら要件に追加） |
| /wp-json/wp/v2/categories | id、name、parent、count | M-32、M-34 | 二階層。同名の子が別の親の下にある（お祭り、グルメ、子育て、イベント）ため「親 > 子」のパスで区別する |
| /wp-json/wp/v2/tags | id、name、count | M-33 | シリーズ企画を束ねている |
| /wp-json/wp/v2/users/<id> | name、slug、link | 著者属性 | 一覧（/users）は 404 で無効化されている。個別は 200。posts の `_embed` で足りるなら個別取得は不要 |

| posts の meta | 使わない | ― | 露出しているのは _tc_wrapper、footnotes、wp-seo-meta-description、wp-seo-meta-robots のみ（2026-11-03 確認）。イベント記事の開催日は本文中の「開催日時」の文章にしかなく、構造化されたフィールドはない。イベント日を基準にした集計は現状では作れない（00_overview.md §3.2） |

### 3.3 著者の扱い

- 保存・表示するのは表示名（name）と著者ページの URL（link、slug から導ける）だけ（NFR-35）。
- WordPress のユーザー ID（数値）は結合にだけ使い、Supabase には保存しない。著者のキーは slug にする。
- メール、ログイン名は REST API に出ないが、仮に出ても保存しない。
- 表示名は実名風とハンドルが混在するが、どちらもサイト上で公開済みの情報。
- ライター本人が非表示を求めた場合の扱いは FR-36（確定、Q-03）。除外する著者の一覧は public リポジトリに置かず、環境変数または Supabase の非公開テーブルに置く（NFR-22、D-10）。窓口と説明の文面は Q-30。

### 3.4 制約

- 認証なし・割当なし。ただし対象サイトへの負荷を避けるため、問い合わせは日次バッチだけ、間隔を空け、差分で取る（NFR-72）。差分取得に使える項目（modified の有無、per_page の上限）は設計で確認する（D-03）。
- 削除・非公開化された記事は API から消える。バッチで「前回あって今回ない」記事を検出し、BI からも消す（FR-72、NFR-34）。
- 規模（2026-11-03 確認）: 公開記事は 225 本。最初の記事は 2025-08-28、定常的な投稿は 2025-10 から（24 本）。直近 12 か月の月間公開本数は 11〜28 本。記事 ID は 4800 前後。
- 著者（2026-11-03 確認）: 公開記事のある著者は 21 人。うち 1 人（表示名 SBC）が 120 本（53%）。次いで 19、17、11、8、6 本。3 本以下の著者が 11 人。表示名 SBC の著者が運営者本人かは未確認（Q-31）。
- カテゴリ（2026-11-03 確認）: 225 本のうち 198 本（88%）が複数カテゴリに属する。多くは「記事」の木と「イベント」の木の両方に子カテゴリを持ち、1 つの親の下でも複数の子を持つ（例: 記事 > イベント、エンタメ、グルメ、暮らし の 4 つ）。「イベント」の木に属する記事は 127 本。重複して数えることが常態になるため、カテゴリ別の集計は親カテゴリを別々の軸として扱う（M-32、Q-15）。
- 対象サイトの WordPress を変更する操作（プラグイン設定など）は本プロジェクトでは行わない。必要なら依頼者に依頼する。

### 3.5 個人情報

- 著者の表示名と著者ページ URL 以外の個人に関する情報は取得・保存しない。
- コメントは扱わない（DS-07 廃止）。

## 4. DS-03 サーバーログ

- ホスティング先は Xserver（sv16640.xserver.jp、nginx。2026-11-03 確認、Q-21 の前半は回答済み）。アクセスログの取得可否は未確認（Q-21）。
- 本要件では使わない（仮）。理由: (1) IP アドレスを含み個人情報の扱いが重くなる、(2) 取得経路（FTP、管理画面）が自動化しにくい、(3) 必要な指標は GA4 で足りる。
- GA4 で計測されない閲覧（JavaScript 無効、広告ブロッカー、ボット）の規模を知る参考にはなるが、初回スコープには含めない。

## 5. DS-04 Google Search Console

- 利用の有無は未確認（Q-09）。
- 検索クエリを出す場合、クエリには個人名や住所が混ざりうるため、除外語としきい値の規則を別に定める必要がある。初回スコープ外（仮）。
- 使う場合の認証は GA4 と同じサービスアカウントで、Search Console 側にユーザー追加が要る（依頼者の操作）。

## 7. 格納先（Supabase）の制約

依頼者の決定（2026-11-03）に基づく制約。技術選定ではない。

- 集計値の格納先は Supabase。日次バッチ（GitHub Actions）が書き込み、BI（Vercel）のサーバー側が読む。ブラウザから Supabase に直接アクセスしない（NFR-42）。
- 格納するのは伏せ処理を済ませた集計値と、記事・著者・カテゴリ・タグのメタデータ（NFR-30〜NFR-35）。生のイベントや個人に関わる値は置かない。
- 保持期間は全期間（仮、Q-05）。GA4 側の保持期間に依存せず、一度取り込んだ値は Supabase に残す（NFR-51）。
- 削除・非公開化された記事に関する行は次のバッチで削除する（NFR-52）。
- 全表で RLS を有効にし、anon ロールの権限は公開用のビューまたは表の select だけ（NFR-43）。スキーマの変更はマイグレーションファイルで行う（NFR-73）。

## 8. 個人情報の扱い

- 原則: 個人を特定できる情報（IP アドレス、ユーザー ID、クライアント ID、メール、フォーム送信内容、サイト内検索語、完全な参照 URL）は取得も保存もしない。個別ユーザーの追跡はしない。
- 例外として扱う個人に関する情報は、著者の表示名と著者ページ URL だけ。理由: サイト上ですでに公開されており、ライター別ビュー（FR-30〜FR-34、FR-36）に不可欠なため。ライター本人の非表示の申し出への対応は FR-36（確定、Q-03。窓口と文面は Q-30）。
- 地域は市までにとどめ、細かい次元で切った小さな値は格納時に伏せる（NFR-33、NFR-37）。
- 規則の原本は .claude/rules/security.md。要件としての ID は 05_non_functional.md §4。

## 9. 指標とデータソースの対応

02_metrics.md §5 の表を正とする。ここでは要点だけ再掲する。

- DS-01（GA4）: M-01〜M-03、M-06、M-09〜M-17。M-41 は GA4 にイベントが届いている場合のみ。
- DS-02（WP REST API、wp/v2 のみ）: M-26、M-30〜M-33、全指標の記事・著者・カテゴリ・タグ次元。
- 派生（DS-01 + DS-02）: M-18〜M-25、M-27、M-32、M-34。
- 要確認: DS-04（M-50）、DS-06（M-41、D-09）。
- 現状は取得不可: DS-05（M-40）。
- 廃止: DS-07（M-42）。M-04、M-05、M-07、M-08 の廃止に伴い、engagedSessions、engagementRate、bounceRate、averageSessionDuration、totalUsers、newUsers は取得しない。
- 対象外: DS-03、DS-08、DS-09、M-43。
