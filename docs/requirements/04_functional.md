# 04 機能要件

- 状態: 草案
- 更新日: 2026-11-03

## 1. 要件の書き方と優先度

- 要件 ID は FR-xx。後工程（設計・テスト）が参照するので振り直さない。削除するときは「廃止」と残す。
- 優先度
  - 必須: 初回公開に含める。
  - 高: 初回公開に含めたいが、未確定事項の回答やデータの確認待ち。
  - 中: 初回公開後でもよい。
  - 低: 要否を含めて未確定。
- 画面案は親エージェントの提案で、依頼者は異議なしだが個別の承認は未取得。確認が要るものは open_questions.md の Q-xx を参照する。
- 各要件に関係する指標 ID（M-xx）と非機能要件 ID（NFR-xx）を書く。
- 技術選定（フレームワーク、ライブラリ、グラフの種類の実装）は書かない。構成（GitHub Actions → Supabase → Vercel）は依頼者の決定として制約に書く（00_overview.md §5）。

## 9. データ取り込み（FR-70〜FR-76）

依頼者の決定: GitHub Actions で日に 1 度実行し、Supabase に格納する。Web サービスとしては公開しない。

| ID | 名称 | 要件 | 優先度 | 関係 |
| --- | --- | --- | --- | --- |
| FR-70 | 日次バッチ | 1 日 1 回、GA4 Data API と WP REST API からデータを取得し、Supabase に格納する。実行時刻は GA4 の日次データが揃う 15:30（プロパティのタイムゾーン）以降で、鮮度の要件（NFR-02）を満たす時刻（仮: 17:00 JST、Q-13）。手動での再実行もできる | 必須 | NFR-01、NFR-02、DS-01、DS-02 |
| FR-71 | 直近 7 日の再取得 | GA4 の遅延データに対応するため、毎回、基準日から過去 7 日分を取り直して上書きする。取り直しで伏せ値の判定が変わる場合の扱いは D-08 | 必須 | NFR-03、NFR-33 |
| FR-72 | 記事メタデータの取り込みと削除の反映 | WP REST API から記事・カテゴリ・タグ・著者（表示名、slug）を取得し、新規・更新を反映する。前回あって今回ない記事（削除・非公開化）は、関連する集計値とともに BI から消す。取得は差分で、間隔を空けて行う | 必須 | NFR-34、NFR-35、NFR-52、NFR-72 |
| FR-73 | 小さな数の伏せ処理 | 細かい次元で切った集計値がしきい値 T（Q-02）未満のとき、格納時に「T 未満」を示す値に置き換える。読み出し側で丸めて済ませない。合計値は伏せる前の値から別に計算して格納する | 必須 | NFR-33 |
| FR-74 | 失敗の通知 | バッチが失敗したら、依頼者の指定する通知先（Q-12）に、失敗した工程と日時を知らせる。通知の文面に API の応答や行データ、秘密情報を含めない | 必須（通知先は Q-12） | NFR-70、NFR-44 |
| FR-75 | 初回のバックフィル | 初回に、指定した開始日（Q-05）から基準日までの GA4 データと、全記事のメタデータをまとめて取り込む。GA4 の割当（D-01）に収まるよう分割して実行できる | 必須 | NFR-50、NFR-61 |
| FR-76 | 実行記録 | バッチごとに実行日時、対象期間、取得・格納した件数、結果（成功 / 失敗と種別）を Supabase に記録し、FR-02 の表示に使う。記録に API の応答や行データを含めない | 必須 | FR-02、NFR-44 |
