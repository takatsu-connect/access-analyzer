# 00 概要（背景・目的・スコープ）

- 状態: 草案
- 更新日: 2026-11-03

## 1. 背景

- 「高津コネクト」（https://takatsu-connect.com/）は WordPress で運営する地域メディアで、複数のライターが記事（投稿）を書いている。投稿頻度はほぼ毎日 1 本。
- アクセスの計測は GA4（gtag.js、測定 ID G-79CFGF83VT）だけで、WordPress 側の統計プラグイン（Jetpack Stats、WP Statistics など）は導入されていない。
- GA4 の管理画面は、権限の付与が要り、記事・著者・カテゴリの軸で見るには設定や操作の習熟が要る。運営者とライターが、ログインなしで、自分たちの言葉（記事、ライター、カテゴリ、シリーズ）で数値を見られる場が欲しい。
- 本プロジェクトは、GA4 と WP REST API の集計値を日次で取り込み、Web の BI として公開するもの。工程は要件定義 → 設計 → 構築 → デプロイで、本文書群は要件定義の成果物。

## 2. 目的

1. 運営者が、サイト全体の傾向（PV、セッション、ユーザー数、流入元、デバイス、地域、曜日×時間帯）を期間比較つきで把握し、編集方針（力を入れるカテゴリ、投稿する時間帯、SNS の使い方）を決められる。
2. ライターが、自分の記事の反応（公開後の立ち上がり、流入元、ロングテールでの再浮上）を、全記事の分布（中央値・四分位）と比べて見られ、次の記事のテーマや書き方に活かせる。
3. どちらもログインなしで見られる。そのために、個人情報とセキュリティ上まずい情報は一切出さない。
4. 投稿活動（本数、カテゴリの偏り）は GA4 に依存せず、WP REST API だけで先に見られる。

## 3. スコープ

### 3.1 やること

- GA4 Data API から日別の集計値を取り込む（DS-01、M-01〜M-17）。
- WP REST API から記事・著者（表示名と著者ページ URL）・カテゴリ・タグのメタデータを取り込む（DS-02、M-30〜M-34）。
- 両者を記事 ID で結合し、記事の立ち上がり曲線と全記事の中央値・四分位を計算する（M-18〜M-22）。
- 集計値を Supabase に格納し、Vercel 上の BI から読んで表示する。画面は 6 種（全体ダッシュボード、記事一覧とランキング、ライター別、カテゴリ・タグ別、投稿活動、反応指標）。要件は 04_functional.md。
- 小さな数を格納時に伏せる、非公開記事を除外する、著者は表示名と著者ページ URL だけ、などの公開データの規則を要件（NFR-30〜NFR-39）として定める。
- 日次バッチの失敗通知と初回のバックフィル（FR-70〜FR-76）。

### 3.2 やらないこと

- リアルタイムの値、個別ユーザーの追跡、IP アドレス・ユーザー ID・完全な参照 URL・サイト内検索語・フォーム送信内容の取得と表示（NFR-32）。
- ログイン機能、利用者ごとの権限、BI 上での設定変更 UI（NFR-20、NFR-22）。
- 対象サイト（WordPress）の設定変更。GA4 のイベント設定や Search Console の登録が必要な場合は依頼者に依頼する。
- 問い合わせフォームの送信数・内容（FR-63、M-43）。
- Search Console の検索クエリ（M-50）。初回スコープ外（仮、Q-09）。
- サーバーログの取り込み（DS-03。仮、Q-21）。
- 広告効果の収益換算、将来予測、異常検知の通知。
- 週次・月次の定期配信（メール、LINE など）。要否は Q-24。
- Universal Analytics 時代のデータの取り込み。
- 技術選定（フレームワーク、ライブラリ）。設計工程で行う。

## 4. 前提（確認済みの事実）

2026-11-03 に親エージェントが確認した事実票に基づく。

- 対象サイトは WordPress 7.1.4、テーマ Snow Monkey、子テーマ takatsuconnect。
- 計測は GA4 の gtag.js のみ（測定 ID G-79CFGF83VT）。Jetpack Stats、WP Statistics、Matomo、Site Kit はトップページから検出されない。
- 主なプラグイン: snow-monkey-blocks、snow-monkey-forms、wp-ulike（いいね）、add-to-any（シェアボタン）、spotlight-social-photo-feeds、official-facebook-pixel。
- WP REST API（/wp-json/wp/v2/）は公開。posts、categories、tags、users/<id>（個別）が取れる。users 一覧は無効化されている。記事 URL は https://takatsu-connect.com/<記事 ID>/。
- カテゴリは二階層（親: イベント、記事、マップ、広告）で、同名の子が別の親の下にある。タグはシリーズ企画を束ねている。
- GA4 プロパティのプロパティ ID は依頼者が控えている。サービスアカウントに閲覧者権限を付与済み。認証は Workload Identity Federation（鍵なし）。
- GA4 の日次データは処理に通常 12 時間、24〜48 時間かかることがあり、遅延データは最大 7 日。日次データはプロパティのタイムゾーンで 15:30 に揃う。
- 未確認: ホスティング先、サーバーログの有無、GA4 の導入時期、データ保持期間、タイムゾーン、API の割当、Search Console の利用、wp-ulike / add-to-any の GA4 イベント、コメント機能の有効性。いずれも open_questions.md に質問として載せている。

## 5. 制約（依頼者の決定、2026-11-03）

技術選定ではなく、要件を満たすうえでの制約として扱う。

- 利用者は運営者と高津コネクトのライター。ライターは「自分の記事がどうか」と「全体としてどうか」を見る。
- ログイン機能は持たせず、誰でも見られる。したがってセキュリティ上まずい情報と個人情報は出さない。
- 全体構成は 2 つに分ける。(1) 情報を取得して Supabase に格納する仕組み。日に 1 度、GitHub Actions で実行し、Web サービスとしては公開しない。(2) Supabase から読む BI。Vercel で動かし、Supabase はブラウザからではなく Vercel のサーバー側から読む。
- リポジトリは public。秘密情報はリポジトリに置かない。
- 公開してよいデータの規則は .claude/rules/security.md が正。要件では NFR-30〜NFR-39 として ID を付けた。
- 技術選定は設計工程で行う。

## 8. 工程と本文書の位置づけ

- 本文書群は要件定義の草案。依頼者の回答（open_questions.md）を反映し、security-auditor のレビューを受けてから「確定」にする。
- 次工程（設計）は 02〜05 の ID を参照して、構成、データモデル、パイプライン、画面、セキュリティ、テスト計画を書く。設計上の判断は ADR（docs/design/adr/）に残す。
- 先行して着手できる範囲: 投稿活動（FR-50〜FR-53）は WP REST API だけで作れるため、GA4 側の確認（Q-05、Q-07）を待たずに進められる。
