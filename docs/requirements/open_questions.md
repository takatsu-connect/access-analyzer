## 1. 使い方

- 要件文書（00〜06）の中で推測で埋めなかった事項をここに集める。各質問に ID（Q-01…）を振り、関係する要件 ID を書く。ID は振り直さない。
- 仮置きが必要な箇所は、要件文書側に「仮: …」と書き、この文書の該当 Q を参照する。回答が得られたら要件文書を更新し、該当 Q を「6. 回答済み」に移す。一部だけ回答があった質問は、本文を書き換えて残す。
- GA4 側の事実（タイムゾーン、プロパティ作成日、データ保持、カスタム次元、拡張計測、月間の規模、デバイス比、市の粒度、イベント名）は、依頼者が実行する GA4 の確認スクリプトの結果で回答する予定。該当する質問にその旨を添えた。
- 優先度の意味
  - 高: 回答がないと設計に入れない、または公開範囲・安全性に関わる。
  - 中: 設計の途中までは仮置きで進められるが、構築前に確定が必要。
  - 低: 構築後でも変更しやすい。初回公開までに確定すればよい。

### Q-10 いいね・シェアの計測（一部回答済み）

- 関係: M-40、M-41、FR-60、FR-61、DS-05、DS-06、D-09
- 2026-11-03 に確認した事実:
  - いいね（wp-ulike）: ボタンは記事ページにあるが、REST API の wp-ulike/v1 には templates のルートしかなく、いいね数は REST では取れない。GA4 イベントも送っていない（記事 HTML の gtag は config だけ）。
  - シェア（add-to-any）: ボタンはある。a2a_config に計測の設定はない。GA4 側にイベントが届いているかは未確認。
  - コメント: 公開コメントは 0 件、comment_status は closed。→ 回答済み（§6）。M-42、FR-62、DS-07 は廃止。
- 質問:
  1. いいね数を BI に出したいですか。出すならサイト側の変更（いいね数を返す REST ルートの追加か、GA4 イベントの送信）が必要で、依頼者側の作業になります。優先度は低のままでよいですか。
  2. add-to-any のシェアが GA4 のイベントとして届いているか。→ GA4 の確認スクリプトの結果（イベント名一覧）で回答予定（D-09）。届いていなければ現状では取れません。
- 仮置き: いずれも「要確認」。回答があるまで設計の対象外とする。

### Q-15 複数カテゴリに属する記事の数え方（本文を書き換え）

- 関係: M-32、M-34、FR-40、FR-52
- 2026-11-03 に確認した事実: 225 本のうち 198 本（88%）が複数カテゴリに属する。多くは「記事」の木と「イベント」の木の両方に子カテゴリを持ち、1 つの親の下でも複数の子を持つ（例: 記事 > イベント、エンタメ、グルメ、暮らし の 4 つ）。「イベント」の木に属する記事は 127 本。「重複して数える」は実質的に常態になる。
- 質問: カテゴリ別の集計を次の形にしてよいですか。親カテゴリ（記事 / イベント / マップ / 広告）を別々の軸として扱い、軸ごとに合計と子カテゴリの内訳を出す。同じ軸の中で複数の子に属する記事は重複して数え、その旨を注記する。軸ごとの合計は「その親に属する記事の合計」になり、サイト全体とは一致しないことを注記する。
- 仮置き: 上の形。
